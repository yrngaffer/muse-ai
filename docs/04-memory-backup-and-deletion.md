# Memory: Backup, Export & Deletion

**Date:** 2026-10-28

This document is both a user guide — how to inspect, add, delete, and wipe what Muse
remembers — and a precise description of the technical model behind it. It describes only
what the Milestone 1 (M1) code actually does. Where a capability is a skeleton or a
planned later milestone, it is labelled **planned (M2)** or **planned (M3)**; nothing here
implies a feature works when it does not.

> **M1 honesty note.** This build was authored on a Windows machine with no JDK, Gradle,
> Android SDK, or device. The APK is produced for free by GitHub Actions
> (`.github/workflows/android.yml`); as of this commit the first CI run has not necessarily
> passed, and nothing below has been exercised on a phone. The memory *logic* (repository +
> crypto transform) is covered by JVM unit tests that CI runs; on-device behaviour (Keystore
> key provisioning, the UI) still needs a device. See `docs/09-feature-status.md`.

---

## 1. What Muse remembers — the three layers

All memory lives in a single Room table, `memories`, with a `layer` discriminator column.
One table keeps the schema simple and portable for a future Windows client (see
`docs/02-architecture-and-model-selection.md` §4). The layers are defined in
`data/memory/MemoryLayer.kt`:

- **PERMANENT** — explicitly approved, stable facts (your name, preferences, goals). Meant
  to persist; intended to require confirmation before storing.
- **EPISODIC** — conversation summaries and events, carrying a timestamp, topic, source, and
  confidence. Subject to a retention limit (see §8 — limit setting exists, enforcement is
  planned).
- **ADAPTIVE** — learned corrections and preferences, with a `reinforcement` counter that
  rises each time the memory is used.

### What each row stores

Every row is a `MemoryEntity` (`data/memory/MemoryEntity.kt`). The columns are:

| Field | Type | Meaning |
|-------|------|---------|
| `id` | `Long` (PK, autogenerated) | Unique row id |
| `layer` | `MemoryLayer` | PERMANENT / EPISODIC / ADAPTIVE |
| `content` | `String` | The text — **plaintext, or ciphertext when `encrypted` is true** |
| `encrypted` | `Boolean` | True when `content` holds AES-GCM ciphertext (see §2) |
| `topic` | `String` | Optional grouping label |
| `source` | `String` | Who wrote it (e.g. `"user"`) |
| `confidence` | `Float` | 0..1 confidence |
| `verification` | `VerificationStatus` | `USER_CONFIRMED` / `ASSUMED` / `MODEL_SUGGESTED` |
| `sensitivity` | `Sensitivity` | `NORMAL` / `SENSITIVE` — drives encryption at rest |
| `reinforcement` | `Int` | Usage counter (adaptive weighting) |
| `createdAt` / `updatedAt` / `lastAccessedAt` | `Long` | Epoch-millis timestamps |

The `VerificationStatus` and `Sensitivity` enums live alongside the layer enum in
`MemoryLayer.kt`. The table is registered in `data/db/MuseDatabase.kt` (`@Database`,
`version = 1`), together with the append-only audit table.

## 2. Where memory lives, and what is encrypted

Memory is a local Room/SQLite database inside the app's private storage. It never syncs; no
network path writes or reads it (online tools and the remote engine are off by default — see
`docs/02` §6). The single gateway to the table is `MemoryRepository`
(`data/memory/MemoryRepository.kt`) — the DAO (`MemoryDao`) is not touched directly by the UI.

**Field-level encryption for sensitive content.** When a memory is stored with
`Sensitivity.SENSITIVE`, `MemoryRepository.remember(...)` seals the text before it ever
reaches the database:

```
val encrypt = sensitivity == Sensitivity.SENSITIVE
val stored  = if (encrypt) secretBox.sealString(content) else content
```

The `SecretBox` (`security/crypto/SecretBox.kt`) is implemented by `AesGcmSecretBox`
(`security/crypto/AesGcmSecretBox.kt`): **AES-256-GCM** authenticated encryption, wire format
`[12-byte IV][ciphertext || 16-byte GCM tag]`, Base64-encoded for storage. The key comes from
`KeystoreKeyProvider` (`security/crypto/KeystoreKeyProvider.kt`), a hardware-backed Android
Keystore AES-256 key (alias `muse_master_key`) that **never leaves the Keystore**. The row's
`encrypted` flag is set to `true` and the stored `content` is ciphertext.

On read, decryption is transparent: `MemoryRepository` maps each row to a `MemoryUi`, calling
`secretBox.openString(content)` for encrypted rows; if decryption fails it shows
`"<decryption failed>"` rather than crashing. Full details of the crypto design are in
`docs/08-security-architecture.md`.

**Scope of encryption in M1 (be precise):**

- Encryption is **field-level**, applied only to the `content` of rows marked `SENSITIVE`.
  Metadata columns (`topic`, `source`, timestamps, `layer`) are **not** encrypted. The whole
  database is **not** encrypted at rest with SQLCipher in M1 — that is sequenced for a later
  verified milestone to avoid a native-build dependency (rationale in `docs/02` §3).
- The crypto transform is **unit-tested on the JVM** with an in-memory key
  (`AesGcmSecretBoxTest`); the Keystore-backed key provisioning itself needs a device and is
  **not yet verified** (`docs/09`, rows 7).
- **There is no UI control in M1 to mark a memory as sensitive.** The Memory screen's "Add"
  always stores `NORMAL` (plaintext) rows — see §5. The `SENSITIVE` encryption path is reached
  programmatically (and is covered by `MemoryRepositoryTest`, which stores and reads back an
  encrypted value). A classifier / UI to flag sensitive memories is **planned (M2)**.

## 3. Sensitive content is excluded from plaintext search

Search is a plain SQL `LIKE` query in `MemoryDao.search(...)`, and it deliberately skips
encrypted rows:

```
SELECT * FROM memories WHERE encrypted = 0
  AND (content LIKE '%'||:q||'%' OR topic LIKE '%'||:q||'%')
  ORDER BY reinforcement DESC, updatedAt DESC LIMIT :limit
```

Because sensitive content is stored as ciphertext, it **cannot** be matched by a substring
search — and the `encrypted = 0` filter makes that explicit. Consequence: encrypted memories
are retrievable in the full list (where they are decrypted for display) but are **never
surfaced by keyword search**, including the recall that feeds the chat context (§7). There is
**no separate vector/semantic index** in M1; "the search index" *is* this DB query.

## 4. Inspecting your memories

Open the **Memory** screen (`ui/memory/MemoryScreen.kt`). It shows:

- A title bar reading **"Memory (N)"**, where N is the live count of all stored memories.
- A row of layer chips (`permanent` / `episodic` / `adaptive`). **These chips choose the
  layer a *new* memory will be added to (§5); they do not filter the list below.** The list
  always shows every memory, newest-updated first (`MemoryDao.observeAll()` ordered by
  `updatedAt DESC`).
- One card per memory showing the (decrypted) content and a metadata line:
  `layer · verification · source`, with a `🔒 encrypted` marker when the row is `SENSITIVE`.
- A per-row trash icon (delete one — §6) and a top-bar sweep icon (clear all — §6).

The screen reads from a `Flow` (`MemoryViewModel.memories`), so adds and deletes appear
immediately without a manual refresh.

---

## 5. Adding a memory

1. Type the text in the **"Add a memory…"** field.
2. Tap a layer chip to pick **permanent / episodic / adaptive**.
3. Tap the **+** button.

This calls `MemoryViewModel.add(...)` → `MemoryRepository.remember(...)` with
`source = "user"` and `verification = USER_CONFIRMED`. The `sensitivity` argument is left at
its default, `NORMAL`, so **memories you add through this screen are stored as plaintext** and
are searchable. (As noted in §2, M1 has no in-UI way to mark an added memory `SENSITIVE`.)

## 6. Deleting memory

### Delete a single memory

Tap the trash icon on a card. This runs
`MemoryViewModel.delete(id)` → `MemoryRepository.deleteById(id)` →
`MemoryDao.deleteById` (`DELETE FROM memories WHERE id = :id`). The row is **removed from the
database entirely** — not flagged or hidden.

### Clear ALL memory

Tap the sweep icon in the top bar. A confirmation dialog appears:

> **Clear all memory?** This permanently deletes every stored memory. This cannot be undone.

Confirming ("Delete all") runs `MemoryViewModel.clearAll()` →
`MemoryRepository.clearAll()` → `MemoryDao.clear()` (`DELETE FROM memories`). Every row is
deleted.

### Deletion also removes it from search

Because search is just the DB query in §3 (no separate index to keep in sync), deleting a row
removes it from search results as a matter of course — there is nothing else to purge in M1.

## 7. Turning memory off — Settings → "Collect memory" (`memoryEnabled`)

The **Settings** screen (`ui/settings/SettingsScreen.kt`, under "Memory & privacy") has a
**Collect memory** toggle bound to the `memoryEnabled` setting, persisted with DataStore in
`data/settings/SettingsRepository.kt` (key `memory_enabled`, **default: on**).

What it actually does in M1 (be precise): the toggle gates whether stored memories are
**recalled into the chat**. In `ui/chat/ChatViewModel.kt`:

```
val memories = if (settings.memoryEnabled) container.memory.search(text) else emptyList()
```

So with it **off**, no memories are injected into the model's context — Muse answers without
consulting memory. Two honest caveats:

- Turning it off does **not** erase anything and does **not** disable the manual **Add**
  button on the Memory screen; existing rows remain until you delete them (§6).
- M1 has **no automatic/background memory collection**: the only code path that writes a
  memory is the manual Add (§5). Automatic capture of facts from conversations is
  **planned (M2)**; once it exists, this toggle is the intended switch to stop it.

## 8. Retention (`episodicRetention`) — enforcement planned

A retention limit for episodic memories exists as a setting: `episodicRetention` in
`MuseSettings` (DataStore key `retention_episodic`, **default 500**), surfaced from
`SettingsRepository`. **However, no code enforces it yet** — there is no trimming/eviction
query in `MemoryDao` or `MemoryRepository`, so episodic rows are not currently capped or
aged out. Automatic enforcement of the limit is **planned (M2)**.

---

## 9. Encrypted export / import — planned (M2)

A portable, encrypted export is **specified but not implemented**. The format is defined in
`docs/02-architecture-and-model-selection.md` §7:

> A single versioned JSON document `{ schemaVersion, exportedAt, memories[], personality }`,
> written through Keystore-backed encryption as a `.muse` file, re-readable by a future
> Windows client.

There is **no export or import code in M1** (`docs/09`, row 9: *Not implemented — format
specified, code = M2*). When built, this will be the only supported way to move memory off
the device, and the Windows-portability plan for it lives in `docs/10-windows-roadmap.md`.

## 10. Backups: OS backup is disabled on purpose

Muse opts **out** of Android's system backup so that private memory and keys are never copied
off the device by the OS. This is wired in `android/app/src/main/AndroidManifest.xml`:

```
android:allowBackup="false"
android:fullBackupContent="false"
android:dataExtractionRules="@xml/data_extraction_rules"
```

and in `res/xml/data_extraction_rules.xml`, which **excludes everything** (`root`, `file`,
`database`, `sharedpref`) from **both** `cloud-backup` and `device-transfer`:

```
<cloud-backup>   <exclude domain="database" path="." /> … </cloud-backup>
<device-transfer><exclude domain="database" path="." /> … </device-transfer>
```

Consequences:

- Your memory database does **not** ride along in Google Auto Backup, and does **not**
  transfer during a device-to-device migration. It does not leave the phone via the OS backup
  system.
- Therefore the **only** backup path is the planned manual encrypted export of §9 — which is
  **not available in M1**. Until then, there is no way to back memory up; treat it as living
  on this device only.

## 11. How to wipe everything

Two reliable ways to remove all memory from the device:

1. **In-app:** open **Memory → sweep icon → "Delete all"** (§6). This empties the `memories`
   table immediately.
2. **Uninstall the app.** Removing Muse deletes its private storage — the Room database
   (`MuseDatabase`) and the DataStore settings — and invalidates the app's Android Keystore
   key (`muse_master_key`). Even if any encrypted row survived in some copy, it becomes
   permanently undecryptable once that key is gone.

For verification and threat context, note that deletion is a hard row delete (no trash, no
tombstone, no separate index), and that nothing is retained off-device because OS backup is
disabled (§10). The kill switch and shutting down automation are covered separately in
`docs/05-disable-all-automation.md`; the data-at-rest threat model is in
`docs/03-threat-model.md`.
