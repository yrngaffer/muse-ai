# Windows Integration Roadmap

**Date:** 2026-10-28 · Forward-looking design. **None of the Windows client, export/import, or sync described here is implemented.** Muse is an Android-only app today, and it transmits nothing off the phone automatically.

---

## 0. Honesty preface (read this first)

This document was written on a Windows development box that has **no JDK, Gradle, or Android SDK and no attached device**. The APK is produced for free by GitHub Actions (`.github/workflows/android.yml`); the first CI run has not necessarily passed, and nothing here has been built, installed, or exercised on a phone. See `docs/BUILD-AND-INSTALL.md` and `docs/01-compatibility-report.md`.

More importantly for this roadmap: **there is no Windows client, no export/import code, and no sync code in the repository.** Everything below is a plan with an explicit security bar it must clear before a single byte moves between devices. The one thing that is real today is a *memory schema that was deliberately kept portable* so that such a client is feasible later. Live status for each capability is tracked in `docs/09-feature-status.md` (export/import is item 9, listed as not implemented).

Milestone 1 reality (what actually runs): an offline, no-model engine (`OfflineRuleEngine`) behind the `InferenceEngine` interface; three-layer Room memory with Keystore AES-256-GCM encryption of sensitive content; the zero-trust security core. On-device LLM and the opt-in remote engine are **planned (M2)**; accessibility automation, SAF file ops, export/import, and sandboxed code execution are **not implemented** (sandboxed execution is deliberately disabled).

## 1. Why a Windows client is even possible: the portable memory schema

The one Android-first decision that makes a future shared memory realistic is that the **memory row model contains no Android-only types.** It is plain data.

`MemoryEntity.kt` (table `memories`, declared in `MuseDatabase.kt`) stores only primitives and portable enums:

| Column | Type | Portable? |
|--------|------|-----------|
| `id` | `Long` (autogenerated) | yes |
| `layer` | `MemoryLayer` enum | yes — plain Kotlin enum |
| `content` | `String` (ciphertext when `encrypted`) | yes |
| `encrypted` | `Boolean` | yes |
| `topic`, `source` | `String` | yes |
| `confidence` | `Float` | yes |
| `verification` | `VerificationStatus` enum | yes |
| `sensitivity` | `Sensitivity` enum | yes |
| `reinforcement` | `Int` | yes |
| `createdAt`, `updatedAt`, `lastAccessedAt` | `Long` (epoch millis) | yes |

The three enums (`MemoryLayer.kt`) are ordinary, string-named value sets with no platform dependency:

- `MemoryLayer { PERMANENT, EPISODIC, ADAPTIVE }`
- `VerificationStatus { USER_CONFIRMED, ASSUMED, MODEL_SUGGESTED }`
- `Sensitivity { NORMAL, SENSITIVE }`

The only Android coupling in `MemoryEntity.kt` is the Room annotations (`@Entity`, `@PrimaryKey`) — annotations on the class, not types in the data. A Windows client simply maps the same columns to its own store; the *values* carry over unchanged. The design rationale is recorded in `docs/02-architecture-and-model-selection.md` §4 and §7.

**Versioning.** The Room database is declared at `version = 1` (`MuseDatabase.kt`). The interchange envelope (next section) carries its own top-level `schemaVersion` so a reader on either platform can detect and migrate an older shape rather than guessing. Today both are v1; the point is that the version is *explicit and travels with the data*.

Personality is equally portable. `Personality.kt` is a `@Serializable` data class (`assistantName`, `ownerNickname`, `tone`, `verbosity`, `humor`, `formality`, `emojiUse`) and is already persisted as JSON (`SettingsRepository` stores it under the `personality_json` DataStore key). No transform is needed to carry it to another client.

## 2. The interchange: a planned encrypted export/import file

The chosen vehicle for moving memory between devices is a **file the user controls**, not a network call. Its shape is specified in `docs/02-architecture-and-model-selection.md` §7:

> A single JSON document `{ schemaVersion, exportedAt, memories[], personality }`, written through Keystore-backed encryption as a `.muse` file. The same JSON can be read by a Windows client.

Properties of this format:

- **Versioned** — `schemaVersion` is the first field, so an importer validates compatibility before touching anything.
- **Self-describing** — `exportedAt` plus the full `memories[]` row set and `personality` block; a reader needs nothing else.
- **Encrypted at rest** — produced via the Keystore-backed `SecretBox` / `AesGcmSecretBox` transform that already protects sensitive memory content on-device (`MemoryRepository` encrypts `SENSITIVE` rows through `SecretBox`). The key provisioning is device-bound through `KeystoreKeyProvider`, which is exactly why a *cross-device* format needs a passphrase-derived or user-supplied key rather than the on-device Keystore key — a detail the export implementation must get right.
- **User-moved** — the user copies the file themselves (USB, their own cloud drive, cable). Muse does not upload it anywhere.

**Status: planned, not implemented.** No export or import code exists in the Android app yet (`docs/09-feature-status.md` item 9 — "Memory export/import (encrypted)" — is not implemented; the format is specified, the code is a later milestone, M2/M3). This roadmap treats the format as the agreed contract, not as a shipped feature.

## 3. Why sync is disabled — and stays disabled until it is built

**There is no sync. The Android app initiates no outbound transfer of memory on its own, ever.** This is not an accident of an unfinished feature; it is the default posture.

Concretely, in the code as it stands:

- The default engine is offline (`OfflineRuleEngine`); it `requiresNetwork = false` via the `InferenceEngine` contract.
- The remote engine and online tools are **off by default** — `SettingsRepository` reads `remote_engine_enabled` and `online_tools_enabled` as `false` unless the user turns them on, and `PermissionBroker.validate` denies any internet-requiring tool while `onlineToolsEnabled` is false.
- There is no background service, sync adapter, or scheduled job in `AndroidManifest.xml` — only `MainActivity`. The `INTERNET` permission is declared but, per the manifest's own comment, is exercised only when the user enables the remote engine or online tools.
- The sole outbound HTTP path is the opt-in `WebFetchTool`, and every request it makes is screened by `UrlGuard` after DNS resolution.

A sync channel is the single largest attack surface such an app could add: it is, by definition, a remote path to the user's most private data and (if ever extended) to the AI's actions. Enabling it before the security model below is fully built and tested would contradict Muse's zero-trust and local-first goals (`docs/02` §1, §6). So sync remains **disabled and unbuilt** until it can meet every requirement in §4. The threat reasoning behind this stance lives in `docs/03-threat-model.md` and `docs/08-security-architecture.md`; the user-facing way to keep everything local is in `docs/05-disable-all-automation.md` and `docs/11-permissions-guide.md`.

## 4. Security requirements any future sync MUST meet

A sync feature ships only if **all** of the following hold. This is the gate, not a wish list. The existing security core (`PermissionBroker.kt`, `UrlGuard.kt`, `PathGuard.kt`, the append-only `AuditLog`, the kill switch in `SecurityPolicy`) is the foundation these build on.

1. **Explicit device pairing.** A Windows client is trusted only after a deliberate, in-person pairing step the user performs on both devices (e.g. short-code or QR confirmation shown on each). No device is ever paired silently or by default.
2. **Strong mutual authentication.** Both ends prove identity on every session — not a shared static secret. Paired devices authenticate each other, not merely the transport.
3. **Encrypted transport.** All traffic uses modern TLS with certificate/public-key pinning between the paired devices; the memory payload stays end-to-end encrypted independent of the transport.
4. **Revocable, device-specific credentials.** Each paired device gets its own credential, shown in a device list, individually revocable. Revoking one device never forces re-pairing the others.
5. **Per-request authorization.** Every sync request is authorized on its own merits — reusing the per-call discipline of `PermissionBroker.validate` (unknown operation → deny, out-of-scope → deny). A valid session is not a blanket grant.
6. **Rate limits.** Requests are bounded per device and per interval, so a compromised or misbehaving peer cannot exfiltrate or hammer at speed.
7. **Replay protection.** Nonces/timestamps/sequence numbers reject replayed or reordered requests.
8. **Immediate disconnect / kill.** The existing kill switch (`SecurityPolicy.killSwitchEngaged`, honored first in `PermissionBroker.validate`) extends to sync: one action severs the channel and drops credentials at once.
9. **Loopback-bound local services.** Any local listener (e.g. LAN pairing helper) binds to loopback (`127.0.0.1` / `[::1]`) or an explicitly paired LAN peer — never `0.0.0.0`. Note `UrlGuard.isDangerous` already blocks *outbound* calls to loopback, RFC-1918, link-local, carrier-grade NAT, and cloud-metadata ranges after DNS resolution; a local sync service is the inbound mirror of that same caution.
10. **Never an unauthenticated AI-control endpoint on the public internet.** Sync moves *memory data* between paired, authenticated devices. It is never a remote endpoint that can drive the agent or invoke tools, and it is never exposed unauthenticated to the open internet. The security invariant stands: the model produces text, and `PermissionBroker` independently validates every tool call — sync cannot become a side door around that gate.

Any requirement that cannot be met and tested (on a real JVM in CI for the logic, and on devices for the transport) blocks the feature. Partial sync does not ship.

## 5. Phased plan

Each phase is strictly gated by the one before it. **Phase 0 is where we are: nothing below exists.**

### Phase 1 — Read-only import of an Android export on Windows
- **Prerequisite:** the Android export half of §2 must exist first (not implemented yet).
- Android writes a `.muse` export file (versioned JSON, §2); the user copies it to the PC by hand.
- A Windows client parses the `schemaVersion` envelope and displays memory and personality **read-only**. It never writes back, and there is no network step.
- Lowest risk: one direction, user-moved file, no live connection, no pairing. Validates that the schema really is portable end to end.

### Phase 2 — Manual two-way export/import
- Both clients can export and import `.muse` files; the user still moves the files manually. **No automatic transfer.**
- Introduces conflict handling: timestamps (`updatedAt`) drive a clear, user-visible merge — reconciliation is a decision the user sees, not a silent overwrite.
- Still no pairing or network channel; risk stays at the level of "a file the user chose to move."

### Phase 3 — Authenticated, paired sync
- A live channel between paired devices, built only after **every** requirement in §4 is implemented and tested.
- Device pairing, mutual auth, pinned encrypted transport, revocable per-device credentials, per-request authorization, rate limits, replay protection, instant disconnect, loopback-bound local services — and never an AI-control endpoint.
- This is the only phase that moves data without the user hand-carrying a file, and it is the last to be built, by design.

## 6. What exists today vs. what each phase needs

| Capability | Today | Needed for |
|-----------|:-----:|-----------|
| Portable memory row model (no Android-only types) | ✅ exists (`MemoryEntity.kt`, `MemoryLayer.kt`) | P1 |
| Portable personality (`@Serializable` JSON) | ✅ exists (`Personality.kt`, `SettingsRepository`) | P1 |
| Keystore AES-256-GCM for sensitive content | ✅ exists (`AesGcmSecretBox`, `KeystoreKeyProvider`) | P1–P3 |
| Versioned export envelope (format spec) | 🟨 specified only (`docs/02` §7) | P1 |
| Android export writer / importer | ⬜ not implemented | P1 / P2 |
| Windows client (any form) | ⬜ does not exist | P1 |
| Cross-device key handling (passphrase-derived) | ⬜ not designed in code | P1–P3 |
| Device pairing + mutual auth + transport | ⬜ not implemented | P3 |
| All §4 sync-security controls | ⬜ not implemented | P3 |

Legend matches `docs/09-feature-status.md`: ✅ implemented · 🟨 partial/spec-only · ⬜ not implemented.

---

## 7. Bottom line

- Muse is Android-only today and **sends nothing off the device on its own.**
- The memory schema was kept portable on purpose, so a Windows client is *feasible* — but not present.
- The interchange is a **user-controlled, versioned, encrypted file**, not a network service, and even that export code is not written yet.
- Sync is **disabled and will stay disabled** until every control in §4 is built and tested. When it arrives, it moves memory between explicitly paired, authenticated devices — and never becomes a remote way to control the AI.
